## 配置与证据

在两个仓库各自的 Settings → Environments → production → Environment variables 配置；现有仓库级 Variables 也兼容，同名环境变量优先。就绪标志是普通配置，SSH 私钥与其他凭据必须保存在 Secrets，不能放在 Variables 或日志中。

| 仓库 | 变量 | 验收后要求的值 | 证据含义 |
| --- | --- | --- | --- |
| my-blog-front | BLOG_BACKUP_RESTORE_VERIFIED | 202611160001_blog_optimization | 正式数据库备份在独立数据库恢复成功，核对数据与迁移范围，并记录备份位置、时间、恢复结果 |
| my-blog-front | BLOG_ADMIN_COMPAT_READY | true | 配对后台候选构建及隔离配对验收通过，发布产物与维护安排就绪；不表示后台必须已经先上线 |
| my-blog-admin | BLOG_API_COMPAT_READY | true | 正式运行的 API 已支持新版后台所需的 header 鉴权、摘要/详情、幂等创建、动态草稿和系列接口，完成实际核验 |

就绪标志不会执行备份或验证 API。合并 PR、单仓 checks 通过和隔离数据库测试不能代替正式环境证据。失效或更换候选时清空对应标志，重新验收。不要为了让流水线变绿而填入 true。

新的检查一次报告所有缺项，在日志生成具名错误，并在 Actions Summary 列出要求、当前状态和处理说明。未满足条件时停止，后续上传、迁移和切换步骤仍不执行。

## 首次发布顺序

1. 完成正式数据库备份及独立恢复验收，记录证据；核对实际生产 API 版本、数据库迁移状态及管理调用方，不能只按 main 已合并判断能力。
2. 按原实施计划先发布 header 验证等兼容 API，再适配后台，最后停用旧接口并强制鉴权。若生产还未部署兼容 API，不把完整汇总版本当作兼容版本直接替代；先准备并评审兼容发布。保持管理维护窗口，旧后台不能向新 API 写入，新后台也不能向旧 API 创建动态草稿。
3. 配对后台候选完成隔离兼容验收、具备发布条件后，记录 BLOG_ADMIN_COMPAT_READY；它不要求后台已先部署，因此不会与后台的正式 API 就绪条件形成相互等待。
4. 每次前台/API 发布满足对应备份和配对条件后，在 main 手动运行部署。核对实际发布标识、HTTP 与业务读取；失败先处理或恢复已验证的安全版本，不继续依赖它的后台发布。
5. 正式 API 能力核验通过后，记录后台 BLOG_API_COMPAT_READY，在后台 main 手动运行部署，随后完成登录、详情、创建、发布/隐藏、系列与上传验收。API/后台版本不匹配期间维持管理维护窗口。

数据迁移继续按新增兼容结构、幂等回填核对、读取切换实施；不修改已应用历史迁移。安全回滚不恢复匿名写入或草稿可读状态。完整要求见 [实施计划](博客优化实施计划.md)。

## 手动运行与重试

在对应仓库 Actions 选择部署 workflow → Run workflow → main。前后台都提供 workflow_dispatch，非 main 手动运行不会执行部署。修改 production 就绪变量后，可手动运行 main，无需为触发部署创建空提交。

Re-run failed jobs 会重新部署该次流水线原来的提交；若 main 已更新，应使用 Run workflow → main，避免发布旧提交。前台每个 attempt 使用独立 release，后台发布加入并发串行控制；运行中的发布不会被新任务取消。

不要自动重跑正式部署来验证本次修复。当前仅通过隔离检查确认缺项、错误值、完整值、Summary 和非 Actions 环境行为；正式恢复验收与真实发布仍待完成。
